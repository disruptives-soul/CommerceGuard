# CommerceGuard v0.4 Staging Pilot

Estado: piloto recurrente staging, sin SaaS/dashboard.

## Objetivo

Correr CommerceGuard de forma recurrente durante 3-5 dias contra staging, con alertas livianas y evidencia confiable.

## Scheduler staging

No-submit, con Slack webhook:

```powershell
$env:CARONE_BASE_URL="https://stg.carone.com.ar"
$env:CG_WEBHOOK_URL="<slack-incoming-webhook-url>"
pnpm.cmd run scheduler -- configs/scheduler.car-one.staging.slack.json
```

Dry-run controlado:

```powershell
$env:CARONE_BASE_URL="https://stg.carone.com.ar"
pnpm.cmd run scheduler -- configs/scheduler.car-one.staging.json --cycles 3
```

## Politica de alertas

Default aprobado:

- `notifyOn`: `COMMERCE_FAILURE`, `MONITOR_FAILURE`.
- `minConsecutiveFailures`: 2.
- `notifyOnRecovery`: true.
- `INCONCLUSIVE` aislado no dispara alerta fuerte.

El payload del webhook no incluye cookies, tokens, headers ni datos personales.

## Slack webhook

Crear en Slack:

1. Crear canal, por ejemplo `#commerceguard-staging-alerts`.
2. Crear una Slack App o usar Incoming Webhooks del workspace.
3. Activar `Incoming Webhooks`.
4. Crear webhook apuntando al canal.
5. Copiar la URL `https://hooks.slack.com/services/...`.
6. Guardarla solo como variable de entorno `CG_WEBHOOK_URL`.

No commitear la URL del webhook.

## Reportes

Reportes historicos separados:

```powershell
pnpm.cmd run report:real -- 50
pnpm.cmd run report:failure-lab -- 50
```

Metrica por ventana:

```powershell
pnpm.cmd run report:window -- --group real --hours 24 --project car-one --env staging
pnpm.cmd run report:window -- --group failure-lab --hours 24
```

Eventos de scheduler:

```powershell
pnpm.cmd run report:scheduler -- --hours 24 --project car-one --env staging
```

Resumen diario operativo:

```powershell
pnpm.cmd run report:daily -- --hours 24 --project car-one --env staging
```

Outputs:

```text
runs/summary.real.md
runs/summary.failure-lab.md
runs/summary.real.24h.md
runs/summary.failure-lab.24h.md
runs/_scheduler/summary.24h.md
runs/daily.md
runs/daily/YYYY-MM-DD.md
```

## Metricas observadas

Cada reporte de ventana incluye:

- total runs;
- `PASS`;
- `COMMERCE_FAILURE`;
- `MONITOR_FAILURE`;
- `INCONCLUSIVE`;
- flakiness;
- avg duration;
- p95 duration;
- retries recovered;
- failed steps;
- ultimas fallas.

## Rutina diaria sugerida

1. Verificar que el scheduler sigue vivo.
2. Ejecutar `report:daily`.
3. Revisar `INCONCLUSIVE`, aunque no hayan alertado.
4. Revisar p95 y compararlo contra la muestra base.
5. Confirmar si hubo alertas webhook y si fueron accionables.
6. Mantener decision humana antes de declarar incidente.

## Criterio para pasar a produccion no-submit

Tras 3-5 dias:

- 0 `COMMERCE_FAILURE` real no explicado;
- 0 `MONITOR_FAILURE` recurrente;
- `INCONCLUSIVE` aislados revisados;
- p95 estable o explicado;
- alertas webhook sin falsos positivos fuertes;
- evidencia suficiente para operar sin dashboard.

## Limites

No incluye:

- dashboard SaaS;
- login/usuarios;
- billing;
- paging fuerte;
- submit productivo;
- automatizaciones comerciales reales.
