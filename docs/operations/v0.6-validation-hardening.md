# CommerceGuard v0.6 Validation Hardening

Estado: endurecimiento operativo del piloto, sin SaaS ni dashboard.

## Objetivo

Demostrar que el piloto recurrente es estable, observable y confiable antes de ampliar cobertura.

No cambia el alcance:

- no dashboard;
- no auth;
- no billing;
- no multi-tenant pesado;
- no submit productivo;
- no tracking de usuarios reales.

## Cambios clave

Cada corrida nueva tiene un `run_id` unico compartido entre:

- `result.json`;
- `report.md`;
- path de evidencia en Supabase Storage;
- `commerceguard_runs`;
- `commerceguard_scheduler_events`;
- `commerceguard_alert_state`;
- Slack alert/recovery/status.

Esto permite reconstruir una corrida o incidente sin correlacion manual por timestamp.

## Migracion Supabase

Ejecutar `supabase/schema.sql` nuevamente en Supabase SQL Editor.

La migracion agrega columnas compatibles:

```sql
alter table public.commerceguard_runs
  add column if not exists run_id text;

alter table public.commerceguard_scheduler_events
  add column if not exists run_id text;

alter table public.commerceguard_alert_state
  add column if not exists last_run_id text,
  add column if not exists last_alert_run_id text;
```

El runtime tiene fallback si estas columnas todavia no existen, pero para trazabilidad completa deben estar aplicadas.

Despues de una corrida:

select

  project_id,

## Test controlado de alerta

Hacerlo solamente con Failure Lab/local o staging controlado. No provocar fallas reales en Car One produccion.

Acceptance:

```text
FAIL 1 -> persisted, no Slack fuerte
FAIL 2 -> persisted, Slack alert
PASS   -> persisted, Slack recovery
```

Comandos base local:

```powershell
cd C:\Users\mnvegalugo\Desktop\commerceguard
$env:CG_MOCK_MODE="BROKEN_CTA"
pnpm.cmd run mock:car-one
```

En otra terminal:

```powershell
cd C:\Users\mnvegalugo\Desktop\commerceguard
pnpm.cmd run scheduler -- configs/scheduler.car-one.local-alert-test.json --cycles 2
```

Esperado:

- dos runs `COMMERCE_FAILURE` o `INCONCLUSIVE` segun evidencia;
- el segundo ciclo emite alerta stdout;
- evidencia queda en `runs/`;
- no hay submit.

Nota: el scheduler local guarda alert state en memoria. Si se reinicia el proceso, no puede probar recovery contra el mismo estado anterior. Para validar recovery completo usar el runtime con Supabase, porque `commerceguard_alert_state` persiste entre ejecuciones.

Para recovery end-to-end:

1. usar un entorno controlado que pueda producir dos fallas alertables con el mismo `project_id`, `environment` y `job_id`;
2. confirmar `last_alerted = true`;
3. correr una ejecucion `PASS` con el mismo trio;
4. confirmar Slack recovery y `last_alerted = false`.

## Reporte operativo ligero

Sin UI:

```powershell
pnpm.cmd run report:daily -- --hours 24 --project car-one --env production-no-submit
pnpm.cmd run report:window -- --group real --hours 24 --project car-one --env production-no-submit
pnpm.cmd run report:scheduler -- --hours 24 --project car-one --env production-no-submit
```

SQL de ventana:

```sql
select
  date_trunc('day', created_at) as period,
  count(*) as total_runs,
  count(*) filter (where product_status = 'PASS') as pass,
  count(*) filter (where product_status in ('COMMERCE_FAILURE', 'MONITOR_FAILURE')) as fail,
  count(*) filter (where product_status = 'INCONCLUSIVE') as inconclusive,
  round(100.0 * count(*) filter (where product_status = 'PASS') / nullif(count(*), 0), 2) as pass_rate,
  avg(duration_ms)::int as avg_duration_ms,
  percentile_cont(0.95) within group (order by duration_ms)::int as p95_duration_ms
from public.commerceguard_runs
where environment = 'production-no-submit'
group by 1
order by 1 desc;
```

## Gate del piloto

Observar `production-no-submit` durante 2 horas a 2 dias.

Con costo cero en Vercel Hobby, el cron corre diario. Si se necesita una muestra mas densa en 2 horas, disparar ejecuciones manuales desde Vercel o usar un runtime externo temporal. No abrir dashboard ni SaaS para esto.

Muestra ideal si hay frecuencia suficiente:

```text
20 a 30 corridas reales
```

Cambiar codigo solamente si aparece:

- falso positivo;
- falso negativo conocido;
- evidencia insuficiente;
- problema de scheduler/runtime;
- selector fragil;
- error de persistencia o alerting.

Al cerrar la muestra:

```text
CommerceGuard Pilot Report

Runs:
PASS rate:
FAIL:
INCONCLUSIVE:
p50:
p95:
False positives:
Scheduler misses:
Evidence failures:
Alert tests:
Recovery tests:

Verdict:
STABLE / NEEDS HARDENING
```
