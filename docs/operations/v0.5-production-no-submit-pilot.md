# CommerceGuard v0.5 Production No-Submit Pilot

Estado: piloto recurrente contra produccion observable, sin submit productivo.

## Objetivo

Validar el funnel publico real de Car One sin generar leads:

```text
Comprar produccion
-> listado real
-> ficha real
-> CTA "Me interesa"
-> modal comercial
-> STOP antes de enviar
```

Esto valida disponibilidad y cambios del front productivo, pero mantiene el guardrail anti-submit.

## Config nueva

Scheduler:

```text
configs/scheduler.car-one.production-no-submit.slack.json
```

Recipe:

```text
recipes/car-one.production-no-submit.json
```

La recipe usa:

```text
https://www.carone.com.ar
```

Car One puede redirigir a:

```text
https://carone.com.ar
```

Por eso la allowlist productiva contempla ambos origins. El flujo sigue siendo no-submit y corta antes de enviar el formulario.

y requiere explicitamente:

```text
CG_PRODUCTION_NO_SUBMIT=true
```

Si esa variable no existe, el runner bloquea la corrida antes de navegar.

## Vercel env vars

Para pasar el cron de staging a produccion no-submit:

```text
CG_SCHEDULER_CONFIG=configs/scheduler.car-one.production-no-submit.slack.json
CG_PRODUCTION_NO_SUBMIT=true
```

Mantener:

```text
CG_WEBHOOK_URL=<slack-incoming-webhook-url>
SUPABASE_URL=https://<project-ref>.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<service-role-key>
SUPABASE_EVIDENCE_BUCKET=commerceguard-evidence
CRON_SECRET=<random-secret>
```

`CARONE_BASE_URL` ya no decide el target de esta recipe productiva. Puede quedar configurada para staging, pero no se usa por `recipes/car-one.production-no-submit.json`.

## Slack

La config productiva no-submit no notifica `PASS` por defecto para evitar ruido.

Notifica:

- `COMMERCE_FAILURE` luego de 2 fallas consecutivas.
- `MONITOR_FAILURE` luego de 2 fallas consecutivas.
- recovery cuando vuelve a `PASS`.

`INCONCLUSIVE` aislado no dispara alerta fuerte.

## Operacion del piloto

Mantener activo:

```text
Vercel Cron -> /api/commerceguard/run -> production-no-submit
```

El cron productivo:

- no genera leads;
- no ejecuta submit;
- no manda Slack por `PASS`;
- alerta solo por 2 `COMMERCE_FAILURE` o `MONITOR_FAILURE` consecutivos;
- manda recovery cuando vuelve a `PASS` despues de una alerta activa.

Ventana de observacion:

```text
2 horas a 2 dias
```

En Vercel Hobby el cron queda diario por costo cero. Para observar una ventana de 2 horas con mas muestra, usar ejecuciones manuales desde Vercel o un runtime externo. No cambiar a SaaS/dashboard para resolver esto.

Mirar cada dia:

- cantidad de corridas;
- `PASS`;
- `COMMERCE_FAILURE`;
- `MONITOR_FAILURE`;
- `INCONCLUSIVE`;
- duracion promedio;
- p95;
- alertas Slack;
- evidencia guardada en Supabase.

SQL operativo:

```sql
select
  date_trunc('day', created_at) as day,
  environment,
  count(*) as total,
  count(*) filter (where product_status = 'PASS') as pass,
  count(*) filter (where product_status = 'COMMERCE_FAILURE') as commerce_failure,
  count(*) filter (where product_status = 'MONITOR_FAILURE') as monitor_failure,
  count(*) filter (where product_status = 'INCONCLUSIVE') as inconclusive,
  avg(duration_ms)::int as avg_duration_ms,
  percentile_cont(0.95) within group (order by duration_ms)::int as p95_duration_ms
from public.commerceguard_runs
where environment = 'production-no-submit'
group by 1, 2
order by 1 desc;
```

Version extendida con notificaciones y evidencia:

```text
supabase/pilot-daily-report.sql
```

Decision despues de 2 horas a 2 dias:

- si esta estable, mantener piloto recurrente;
- si falta cobertura, sumar segundo journey;
- si falta frecuencia, pasar a mayor frecuencia no-submit;
- si hay ruido, ajustar evidencia/selectores/politica antes de ampliar.

## Test manual desde Vercel

1. Confirmar deploy `Ready`.
2. Ir a Vercel -> Settings -> Cron Jobs.
3. Ejecutar `Run` en `/api/commerceguard/run`.
4. Ver Logs filtrados por `/api/commerceguard/run`.

Esperado:

```json
{
  "projectId": "car-one",
  "environment": "production-no-submit",
  "results": [
    {
      "jobId": "buy-interest-production-no-submit",
      "productStatus": "PASS",
      "status": "PASS"
    }
  ]
}
```

## Validar Supabase

```sql
select
  created_at,
  project_id,
  environment,
  journey_id,
  product_status,
  status,
  duration_ms,
  evidence_base_path,
  current_url
from public.commerceguard_runs
order by created_at desc
limit 10;
```

Debe aparecer:

```text
environment = production-no-submit
product_status = PASS
status = PASS
```

Evidencia:

```sql
select
  created_at,
  bucket_id,
  name,
  metadata
from storage.objects
where bucket_id = 'commerceguard-evidence'
  and name like 'car-one/production-no-submit/%'
order by created_at desc
limit 20;
```

## Rollback a staging

Cambiar en Vercel:

```text
CG_SCHEDULER_CONFIG=configs/scheduler.car-one.staging.slack.json
```

Opcionalmente remover:

```text
CG_PRODUCTION_NO_SUBMIT
```

## Limites

No valida:

- submit real;
- CRM/leads reales;
- seguimiento comercial;
- integraciones privadas posteriores al submit.

Si Car One aprueba un lead test manual, usar solamente la recipe controlada de submit en staging o un flujo productivo explicitamente aprobado fuera del cron recurrente.
