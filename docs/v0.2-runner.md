# CommerceGuard v0.2 Runner

v0.2 sigue siendo runner tecnico, no SaaS.

## Clasificacion producto

Cada corrida conserva el estado tecnico (`status`) y agrega `productStatus`:

```text
PASS
COMMERCE_FAILURE
MONITOR_FAILURE
INCONCLUSIVE
```

Reglas:

- `PASS`: el journey llega al STOP configurado.
- `COMMERCE_FAILURE`: falla el journey comercial observable.
- `MONITOR_FAILURE`: falla configuracion, runner, receta o guardrail.
- `INCONCLUSIVE`: timeout, red, challenge, bloqueo, dependencia ambigua o recuperacion por retry.

## Repeat Runner

```powershell
pnpm.cmd run run:repeat -- recipes/car-one.template.json --count 20
```

Genera un reporte en:

```text
runs/_repeat/<timestamp>/summary.md
runs/_repeat/<timestamp>/summary.json
```

Incluye:

- total runs;
- conteos por `productStatus`;
- duracion promedio;
- p95 duration;
- failed steps;
- flakiness;
- retries recuperados;
- rutas de evidencia.

## Reporte Historico

```powershell
pnpm.cmd run report:runs 20
```

Escribe:

```text
runs/summary.md
```

Incluye tabla por corrida, reason, failed step, duracion, vehiculo seleccionado y path de evidencia.

## Retry Controlado

El retry es de journey completo. No se repiten clicks dentro de un step.

```text
PASS -> ok
FAIL + FAIL -> incidente candidato
FAIL + PASS -> INCONCLUSIVE / intermittent
```

## Guardrails Anti-submit

Por defecto, produccion nunca puede hacer submit.

Para una receta con submit se requiere:

```text
safeSubmit: true
CG_ALLOW_SUBMIT=true
baseUrl dentro de allowedBaseUrlPrefixes
```

La receta `recipes/car-one.submit-controlled.template.json` solo permite local/staging.

## Separacion

- Core runner: `src/runner`, `src/config`, `src/evidence`.
- Reporting: `src/reports`.
- Car One recipes: `recipes/car-one*.json`.
- Failure Lab local: `src/dev`, `recipes/car-one.failure-lab-local.json`.

El proximo journey deberia requerir una receta nueva y, como maximo, selectores/STOP propios; no cambios profundos en el core.
